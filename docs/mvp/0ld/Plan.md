## Problem Statement

NHS clinical audits require extracting structured data from electronic medical record (EMR) databases and populating standardised Excel audit templates. This is currently done manually in two ways: (1) BI analysts write SQL queries by hand, export tables to Excel, and pass results to clinicians to fill the template; (2) clinicians manually read through 50+ PDF patient record exports per audit cycle. Both workflows are slow, error-prone, and consume clinical/technical time that neither group has to spare.

Intero automates Path 1 (SQL extraction) for v1: an AI agent queries the local EMR database, matches data to each audit template cell, and produces a fully-populated, fully-traceable audit workbook. Every populated cell links to the source record, the SQL query used, and a timestamp. Missing or ambiguous values are flagged explicitly, never imputed.

## Status Quo

**SQL-based audit path (v1 target):**

1. Clinical team or audit coordinator requests an audit  
2. BI analyst receives request, writes SQL queries against Trust EPR/database  
3. BI exports query results to Excel  
4. BI analyst or clinician manually populates the audit template from the export  
5. Repeat for each audit field — often tens of fields per audit, multiple audit cycles per year

**PDF-based audit path (v2, deferred):**

1. EPR system exports patient records as PDFs (50+ documents per audit cycle)  
2. Clinician reads each PDF manually, locates relevant data for each template cell  
3. Clinician fills in the template by hand — This path is deferred to v2. Higher clinical risk, higher engineering complexity, different buyer.

The SQL path's real cost: BI team bandwidth is a bottleneck for every audit. Requests queue up. Doctors chase BI for data. Audit completion is delayed. BI analysts spend their days doing work that an agent can do.

## Constraints

- Patient-identifiable data must not leave the local Trust environment — local deployment only  
- Agent must not modify records — read-only enforced at SQLite level  
- Missing values must be explicitly labeled (missing / unknown / not\_available)  
- Every populated value must be traceable: source record \+ field \+ SQL query \+ timestamp  
- Extraction blocked until audit template structure is confirmed valid  
- Human escalation required for missing data, low confidence values, schema ambiguity

## Recommended Approach

**Approach A — Demo-Ready SQL Extractor.**

The codebase already has most of this: FastAPI backend, read-only SQL tools, OpenCode agent workflow, Svelte frontend with workbook view. The gap is polish: cleaner audit template upload, more robust SQL generation per cell, clearer MISSING state handling, and a presentable export.

The engineering sprint is 1-3 weeks. The remaining calendar time (targeting first demo within 4-6 weeks) is outreach and demo scheduling — contacting the BI analyst, getting IG clearance for de-identified data, and finding a real audit template to test against. These are parallel tracks, not sequential.

**Key changes to make:**

- Audit template upload: parse column headers from an Excel template → present field list to agent  
- SQL generation: agent proposes SQL per field → Svelte frontend presents each query in an editable code block → BI analyst approves as-is, edits, or rejects → rejection marks the cell MISSING with reason "analyst declined" → only approved queries execute  
- MISSING handling: explicit flag \+ reason for every non-populated cell  
- Export: populate the original Excel template with values \+ a "Sources" tab with full traceability  
- Demo script: 10-minute end-to-end on a synthetic EMR dataset the BI analyst can trust
